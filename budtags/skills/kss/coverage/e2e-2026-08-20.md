First full import of every KSS entity through the real Budtags importers (`kss:e2e-verify`, KSS-INTEGRATION
WU-15), against `https://api.test.kssdata.com/api/v1` with the SupplierID-61 sandbox key. Everything below is
MEASURED on that run, not sampled by a probing script, so it supersedes the sample-limited numbers in
`mapping-findings-2026-08-19.md` where the two disagree.

**`/customerPricing` is the endpoint that does not fit.** It is a forward-looking quote sheet per customer per
product, requested 25 `CustomerIDs` at a time, and at 435 rows per customer the full 2,575-customer sweep is
**~1.12M rows and ~2,240 requests — over two hours of key budget for one entity.** Even a fully-unchanged
sweep costs one conditional page-1 request per customer batch (103). Any integration that polls this endpoint
on a short cadence will spend most of its budget there; narrow the customer set or run it daily.

**Budget consequence — the single most important operational finding.** The key allows **1028 requests/hour**
(`ratelimit-limit`, with `ratelimit-remaining` and `ratelimit-reset` on every response). The window is
SLIDING: `remaining` recovers gradually as individual requests age out an hour after they were made, and
`ratelimit-reset` counts down to the next recovery tick, not to a full refill — so a burst is repaid over the
following hour rather than forgiven at a flip. A full unwindowed walk does NOT fit in one hour: `/invoices` alone is
~21,100 rows and its two id-filtered line endpoints are requested 40 ids at a time, i.e. `2 × ceil(21100/40)`
≈ **1,055 requests for the invoice lines by themselves**. Any first/backfill import must either window the
invoice feed (a row-level `InvoiceLastUpdated` cutoff narrows the LINE fetches, which is where the cost is) or
be spread across hours. The 90-day window used here cost 306 requests for the whole invoice entity, and the 14
bounded entities together cost ~500 requests / ~20 minutes.

## Wire corrections (the mapping doc / earlier coverage was wrong or sample-limited)

1. **`/inventory/batches` UIDs are one per BATCH CODE, not one per row.** 1,117 rows carry **427 distinct
   UIDs** (7 rows carry none), and 427 batch codes map 1:1 onto those tags — one UID repeats up to 13 times
   across a code's location/FIFO rows. The earlier "each row has its OWN UID" reading is wrong; a mirror
   built on distinct UIDs is expected to hold ~427 rows for a 1,117-row walk, not ~1,117.
2. **`purchaseTrans.PalletTag` and `inventory/batches.UID` are DIFFERENT Metrc tag spaces, and never
   intersect.** Both are valid 24-character tags (100% format validity, measured over 4,466 pallet tags and
   427 UIDs), but pallet tags come from the shipper's licence blocks (`1A406030000B0A1…`) and batch UIDs from
   KSS's own (`1A406030003D735…`): KSS re-tags goods into its own inventory on receipt. Overlap measured over
   the full sets: **0 of 4,466**. Consequences: a purchase-line reconciliation joins pallet tags to the
   SELLER's own packages (which is what Budtags' recon does), and any product bridge bootstrapped from batch
   UIDs will find nothing in a seller's package table — the pallet tags are the tag space that can match.
3. **`/retailerInventory` repeats ~1% of rows across page boundaries.** 67,417 rows arrived for 66,759
   distinct `ID`s over a 135-page walk: the endpoint paginates a set that shifts underneath a long walk.
   Harmless for an upsert-on-id importer; fatal for any consumer that assumes page-disjoint results.
4. **Customer licence quality is better than the page-1 sample suggested.** Of 2,575 customers, **510 carry a
   JSON-null `LicenseNum`** and 2,065 carry a value; **93% of the values** match the California `…-LIC` shape.
   The misses are real-world variety rather than corruption: `DCC-10004524` (the newer DCC numbering),
   `C10-18-0000092-TEMP` (temporary licences), one lower-case-L typo (`C9-0000510-LlC`), and the known test
   placeholders (`LIC-99999-FAKE`, `OUS`, `State Partner`, `=`). An importer must tolerate all of it — and
   must not count the 510 nulls as malformed.
5. **`/promotionsProducts` still returns HTTP 500** (2026-08-20), unchanged since 2026-08-19. The probe costs
   ~80 seconds because the client backs off 5xx before giving up.

**The 70% batch join is a ceiling, not a defect.** `/inventory/batches` is inventory-scoped: a sold-out batch
disappears from it. Depletion lines reach back 90 days, so a third of them name batches that no longer exist
upstream — the earlier 76.9% "sample-limited, re-run with a full batch walk" note is answered here, with a
FULL batch walk, and the number went DOWN. The join rate is a function of how long the mirror has been
harvesting, which is exactly why batches must be captured continuously and never deleted on absence.

## Behavior confirmations

- **ETag / conditional GET works end to end**: a `sync_recent` walk of `/products` costs 2 requests, and the
  immediately following walk costs 1 — page 1 answers 304 and the walk short-circuits (50% fewer requests on a
  2-page endpoint; the saving scales with page count).
- **Idempotency**: a second full import reported `0 new / N updated` for every entity. The single exception is
  `/inventory`, which publishes no row id and is stored as a per-walk generation, so a re-run adds one
  generation (484 rows) by design.
- **Money**: 2,640 invoices dated inside a 90-day window totalled **$9,387,041.40**, against the $9.71M/90d
  measured on 2026-08-19 for a window one day earlier — the feed is stable.
- **Payments**: 1,927 payment rows, 2,103 applications; `/arAging` produced 358 accounts and 1,511 bucket
  children.

## Implementation hazards this run exposed (both fixed in Budtags)

1. **`whereIn` over an unbounded pending set dies at MySQL's placeholder limit.** Deciding "new vs updated"
   with one `whereIn` over every walked id fails with `SQLSTATE[HY000] 1390 Prepared statement contains too
   many placeholders` once a feed passes 65,535 rows — `/retailerInventory` (66,759) does. Chunk the lookup.
2. **Materializing the whole walk exhausts a 512M import limit.** Holding 67,417 wire rows AND a mapped copy
   of each blew the memory limit mid-flush. `/retailerInventory` is the only KSS feed that requires page-by-page
   streaming with a per-page flush; every other feed fits comfortably.
